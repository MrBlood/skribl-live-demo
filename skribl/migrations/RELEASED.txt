# SHA-256 of every RELEASED Alembic revision.
#
# A released migration must NEVER be edited: a database that already ran it is
# stamped at that revision, so `alembic upgrade head` sees itself as current and
# executes nothing. The change then applies only to databases that never had the
# problem, and silently skips every deployment that did.
#
# This project learned that twice. The v135 backfill was added by editing
# 86171614cb85 in place; the v137 corrections were added by editing
# e4b7c9a15d2f in place. Both were no-ops exactly where they were needed.
#
#
# a2f6c8b30e14's digest changed once, the day it was written, and the reason is
# the one case this file's rule does not cover: IT HAD NEVER SUCCEEDED ANYWHERE
# DURABLE. Its backfill read every payload into Python 200 rows at a time and
# ran the production box out of memory -- the Procfile is
# `alembic upgrade head && gunicorn app:app`, so the deploy died before the
# server started and the host kept serving the previous build. The revision
# rolled back, so no durable database was ever stamped at it.
#
# That is what makes editing it right rather than forbidden. The rule above
# exists because an edited migration is a SILENT NO-OP for any database that
# already ran it; here there is no such database, and adding a new revision
# would not have helped either -- `upgrade head` runs this one first and it
# would have run out of memory again before reaching the fix.
#
# b5c1e7d92a34's digest changed TWICE, both times within a day of being written,
# both times for the same reason a2f6c8b30e14's did: IT HAD NEVER SUCCEEDED
# ANYWHERE DURABLE. Each attempt exited the deploy before gunicorn started, so
# the revision's transaction rolled back and no database was ever stamped at it.
# A new revision could not have helped either time -- `upgrade head` runs this
# one first, and it would have failed again before reaching the fix.
#
# THE FIRST EDIT fixed a cast that ran before the guard written above it. The
# PostgreSQL backfill guarded two casts with json_typeof() checks written above
# them, which reads like a funnel and is not one: PostgreSQL sorts WHERE quals
# by estimated cost and is free to run a cast before the guard meant to protect
# it, and EXPLAIN showed the regex hoisted above every json_typeof. One post
# whose cssWidth was an object gave
#
#     invalid input syntax for type numeric: "{"a":1}"
#
# THE SECOND EDIT removed the backfill from this revision altogether, because
# the rewritten SQL was correct and the deploy died anyway:
#
#     psycopg.OperationalError: consuming input failed:
#     SSL error: unexpected eof while reading
#
# The backend went away mid-statement. Every JSON operator on a `json` column
# detoasts and re-parses the WHOLE document, and the statement called five of
# them per row -- so a table of multi-megabyte drawings was parsed five times a
# row, in one statement, on a small instance. Correct SQL, fatal cost, which is
# the v307 out-of-memory lesson moved from Python into the database.
#
# WHAT THE SECOND FAILURE ACTUALLY TAUGHT, and the reason this note is long:
# the bug was never the SQL. It was that COSMETIC DATA WORK SAT IN THE DEPLOY'S
# CRITICAL PATH. `Procfile` is `alembic upgrade head && gunicorn app:app`, so
# anything in an upgrade() can take the site down, and what this one computed
# was a nicer crop for old tiles. A null canvas size is a supported state; a
# post that has not been backfilled looks the way it did last week.
#
# So upgrade() now adds two nullable columns and returns -- a catalogue update
# that reads no payload and cannot run out of memory or time. The backfill is
# `python -m skribl.backfill_canvas`, batched, id-paged, resumable and safe to
# interrupt, run when somebody chooses rather than while a release waits on it.
# verify_migrations asserts BOTH halves: that upgrade() calls nothing but
# op.add_column, and that the command survives the hostile payload shapes a real
# gallery holds. verify_postgres drives the same command against a real cluster.
#
# verify_migrations.py fails if any digest below changes. To change migration
# BEHAVIOUR, add a revision. To add a genuinely new revision, append its digest.
#
# f0a3d81b47e2's digest changed once, in v141: BATCH 500 -> 25, after v140
# was recalled unreleased. Batch size cannot change which rows result;
# verify_migrations.py proves it at several sizes.
#
# b7d240ac91e3's digest changed once, in v280, and ONLY its downgrade().
# `upgrade()` is byte-identical -- proved, not asserted: the UPGRADE-PATH
# stanza at the foot of this file pins every released upgrade() as a normalised
# AST, and verify_migrations.py fails if one moves. That is the check the
# paragraph above is really about.
#
# THE RULE'S OWN REASONING INVERTS FOR A DOWNGRADE. "A database that already
# ran it is stamped at that revision, so upgrade head executes nothing" is why
# editing an upgrade() is useless. A downgrade() is READ FROM THE FILE at the
# moment somebody downgrades, so editing one reaches every stamped database --
# it is the only thing that does.
#
# Adding a guard in a NEW revision on top was considered and does not work: a
# database stamped at b7d240ac91e3 never runs a later revision's downgrade(),
# and those are exactly the v279 deployments the guard exists for.
#
# WHAT IT WAS PROTECTING AGAINST, measured rather than assumed. The v279
# downgrade refused non-numeric user_ids on PostgreSQL and returned before the
# check on SQLite. On SQLite the rebuild does not preserve them:
#     '3f2a-9c11-uuid' -> 3      'abc-def'    -> 0
#     '01ARZ3NDEKTSV4' -> 1      'auth0|60f1' -> 0      'a@b.com' -> 0
# Three of those collapse to the SAME owner, so each of those users could then
# delete the others' posts. Silent authorship reassignment, which is worse than
# the failed migration the guard produces instead.
#
