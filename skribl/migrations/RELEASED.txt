# SHA-256 of every RELEASED Alembic revision.
#
# A released migration must NEVER be edited: a database that already ran it is
# stamped at that revision, so `alembic upgrade head` sees itself as current and
# executes nothing. The change then applies only to databases that never had the
# problem, and silently skips every deployment that did.
#
# This project learned that twice. The v135 backfill was added by editing
# 86171614cb85 in place; the v137 corrections were added by editing
# e4b7c9a15d2f in place. Both were no-ops exactly where they were needed.
#
# verify_migrations.py fails if any digest below changes. To change migration
# BEHAVIOUR, add a revision. To add a genuinely new revision, append its digest.
#
# f0a3d81b47e2's digest changed once, in v141: BATCH 500 -> 25, after v140
# was recalled unreleased. Batch size cannot change which rows result;
# verify_migrations.py proves it at several sizes.
#
# b7d240ac91e3's digest changed once, in v280, and ONLY its downgrade().
# `upgrade()` is byte-identical -- proved, not asserted: the UPGRADE-PATH
# stanza at the foot of this file pins every released upgrade() as a normalised
# AST, and verify_migrations.py fails if one moves. That is the check the
# paragraph above is really about.
#
# THE RULE'S OWN REASONING INVERTS FOR A DOWNGRADE. "A database that already
# ran it is stamped at that revision, so upgrade head executes nothing" is why
# editing an upgrade() is useless. A downgrade() is READ FROM THE FILE at the
# moment somebody downgrades, so editing one reaches every stamped database --
# it is the only thing that does.
#
# Adding a guard in a NEW revision on top was considered and does not work: a
# database stamped at b7d240ac91e3 never runs a later revision's downgrade(),
# and those are exactly the v279 deployments the guard exists for.
#
# WHAT IT WAS PROTECTING AGAINST, measured rather than assumed. The v279
# downgrade refused non-numeric user_ids on PostgreSQL and returned before the
# check on SQLite. On SQLite the rebuild does not preserve them:
#     '3f2a-9c11-uuid' -> 3      'abc-def'    -> 0
#     '01ARZ3NDEKTSV4' -> 1      'auth0|60f1' -> 0      'a@b.com' -> 0
# Three of those collapse to the SAME owner, so each of those users could then
# delete the others' posts. Silent authorship reassignment, which is worse than
# the failed migration the guard produces instead.
#
