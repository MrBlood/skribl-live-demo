# 'pip install -r requirements.txt' followed by 'pip freeze' and 'pip download'.

# INSTALL WITH:
#     pip install -r constraints.txt --require-hashes
#
# NOT '-r requirements.txt -c constraints.txt': --require-hashes demands == pins
# on every requirement, and requirements.txt carries ranges. That command fails
# with "all requirements must have their versions pinned with ==". This file is
# the fully-pinned lock; requirements.txt stays the human-readable range spec.
#
# These hashes are for linux x86_64 / cp312 wheels. A different platform needs a
# regenerated file — that is why requirements.txt tells you to generate the lock
# on the real deployment target rather than trusting this one blindly.
#

# reported GHSA-g6x2-hccm-hh4m against 3.1.8 (safe_join accepted Windows device
# names; Windows hosts only). The hash is the wheel's, checked against PyPI's.
#

# pyasn1_modules, pycparser, pyOpenSSL) on 2026-11-10: the site's passkeys
# (social/passkeys.py). Each hash is the wheel `pip download` fetched in this
# container, except cryptography's, which is its manylinux2014 (glibc 2.17)
# wheel rather than the glibc 2.34 one pip prefers here: a hashed install
# takes the wheel whose hash is listed (checked in a fresh venv), and the
# older baseline installs on any build image this lock already runs on.
# cbor2 6.2.1 ships only a glibc 2.28 wheel, the same baseline greenlet's has.
#
# Regenerated 2026-08-07 — the previous copy predated
